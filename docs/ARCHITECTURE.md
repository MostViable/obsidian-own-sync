# Архитектура

Этот документ описывает **планируемую** систему. Реализованные части отмечаются в [STATUS.md](STATUS.md).

## Границы системы

```text
Obsidian на каждом устройстве
  └─ Плагин: TypeScript, Obsidian API
       ├─ Механизм синхронизации
       ├─ VPS (первый релиз): шифрование ── HTTPS ─── Rust-сервер пользователя
                                           ├─ SQLite: версии, пользователи и права
                                           └─ каталог: зашифрованные объекты
       └─ GitHub (позже): обычные файлы ── GitHub API ── приватный репозиторий
```

У проекта нет общего сервера для пользовательских заметок. Первый релиз обращается только к VPS, который указал пользователь. Запланированный позднее GitHub-режим будет обращаться к GitHub напрямую.

## Клиент

- Плагин пишется на TypeScript и собирается в JavaScript через esbuild. Код, выполняемый внутри Obsidian, не использует Node.js или Electron API: они недоступны на мобильных устройствах.
- Работа с обычными файлами vault идёт через Obsidian API. Доступ к скрытым файлам, если понадобится, рассматривается отдельно.
- Один механизм отвечает за учёт локальных изменений, сравнение версий, очередь отправки и разрешение конфликтов. В первом релизе данные шифруются перед отправкой на VPS. Модель версий и формат учитывают историю, общие vault и ключи; будущий GitHub-адаптер должен сохранять правила конфликтов без обещания общего формата хранения.
- Запуск синхронизации планируется после открытия vault, при возвращении в Obsidian и после изменений, пока приложение открыто. Работа при закрытом мобильном приложении не обещается.
- Токены и ключи не записываются в обычный `data.json` плагина; для них используется Obsidian `SecretStorage`. Код подключения нового устройства не должен содержать действующий токен другого устройства.

## Удалённое состояние

Контракт ревизий и безопасного повтора описан в [REVISION_CONTRACT.md](REVISION_CONTRACT.md). До реализации записи пользовательских данных нужно определить весь протокол синхронизации:

1. Прочитать идентификатор vault и текущую ревизию.
2. Получить изменения после известной ревизии и нужное содержимое файлов.
3. Передать новое содержимое безопасно для повторной попытки.
4. Применить набор изменений **только к ожидаемой ревизии**. Если ревизия изменилась, перечитать удалённое состояние и повторно согласовать изменения.

Формат данных и сетевой протокол получают номер версии. Удаления хранятся как записи об удалении до безопасной очистки истории. Ревизии и контрольные суммы важнее времени изменения файлов: часы устройств могут расходиться.

### Личный VPS — первый релиз

- Сервер: Rust, Axum, SQLite и каталог для содержимого файлов. TLS перед сервером обеспечивает Caddy или уже настроенный пользователем reverse proxy.
- Сервер хранит ревизии и зашифрованные объекты, проверяет ожидаемую ревизию при записи и выдаёт отдельные отзывные права каждому пользователю и устройству.
- Шифрование выполняется на клиенте до передачи. Для первого публичного релиза нужны безопасное подключение новых участников, резервная копия или фраза восстановления ключа и ротация после отзыва доступа; точный протокол фиксируется до реализации. Потерянный ключ без резервного способа восстановления сервер вернуть не сможет.
- Первая поставка должна запускаться из готового релиза без установки Rust на VPS. Docker остаётся дополнительным способом установки.
- Один экземпляр предназначен для личного или небольшого общего vault. Если позже понадобится общий облачный сервис проекта, его база и эксплуатация проектируются отдельно; протокол клиента должен оставаться совместимым.

### GitHub после self-hosted релиза

- Один выделенный приватный репозиторий на vault. Markdown-файлы остаются читаемыми через GitHub; в этом режиме нет сквозного шифрования. Служебные данные хранятся отдельно от заметок.
- Подключение планируется через GitHub App с доступом к выбранному репозиторию. Автоматическое создание репозитория потребовало бы более широких прав, поэтому первый мастер может открыть страницу создания репозитория и затем подключить его.
- Несколько изменений объединяются в один commit. Обновление ветки не должно быть принудительным; при одновременной записи адаптер повторяет согласование.
- Размеры вложений и частота отправки учитывают ограничения GitHub. Поведение для слишком больших файлов определяется до релиза GitHub-режима, без тихого пропуска.
- Для общего vault участники получают доступ к репозиторию через GitHub. Плагин не скрывает от них содержимое или историю коммитов.

## Правила сохранности данных

- При конкурирующих правках ни одна версия не исчезает молча. Простое текстовое объединение допустимо только при известной общей базе; иначе создаётся копия конфликта.
- Удаление одного устройства не побеждает неотправленную правку другого без сохранения обеих операций.
- Сбой сети, закрытие приложения и повтор запроса не должны создавать потери или незаметные дубликаты.
- Первое подключение существующего vault требует явного выбора источника и предварительной копии данных.
- Состояния «синхронизировано», «в очереди», «конфликт» и «ошибка» должны быть видны в плагине.
- Настройки `.obsidian` и секреты не включаются автоматически в технический MVP. Их выборочная синхронизация входит в первый публичный релиз. Собственные секреты и локальное состояние плагина не передаются. `data.json` стороннего плагина может содержать токены, поэтому его передача требует явного выбора и предупреждения. Межплатформенное поведение и правила переноса исполняемого кода сторонних плагинов проверяются отдельно.
