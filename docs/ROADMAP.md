# Дорожная карта

Этап считается завершённым только после проверки его критериев. План может меняться по результатам прототипов; изменения фиксируются в [DECISIONS.md](DECISIONS.md).

Базовые проверки описаны в [MVP.md](MVP.md), а обязательный объём первого публичного релиза — в [RELEASE_V1.md](RELEASE_V1.md). Этапы 1–4 дают внутренний технический MVP; GitHub-режим проверяется раньше как alpha.

## 0. Основа проекта

- [x] Создать локальную папку и начальные документы.
- [x] Создать приватный рабочий репозиторий GitHub.
- [x] Завести issues для проверок первого этапа.
- [x] Выбрать имя и лицензию, затем открыть репозиторий.
- [ ] Добавить шаблоны задач и CI по мере появления кода.

**Критерий рабочего старта:** документы доступны в публичном GitHub-репозитории, проверки первого этапа заведены как issues.

## 1. Проверка ключевых ограничений

- [ ] Собрать минимальный плагин на desktop, Android и iOS, работающий с файлами через Obsidian API.
- [ ] Проверить GitHub App: вход, доступ к выбранному репозиторию, обновление токена.
- [ ] Проверить запись нескольких файлов одним GitHub commit и отказ от записи при изменении удалённой ветки.
- [ ] Зафиксировать версию формата и контракт адаптеров с учётом истории, участников, открытого GitHub и зашифрованного VPS до написания сервера.
- [ ] Проверить доступ к выбранным файлам конфигурации на desktop и mobile и схему подключения участников к обоим backend.

**Критерий:** два устройства читают один тестовый vault; конкурирующая запись не затирает первую.

## 2. Общий механизм синхронизации

- [ ] Учёт версий, очереди, удаления, восстановления после ошибки и конфликта.
- [ ] Тесты на одновременные правки, переименование, удаление, обрыв сети и повтор операции.
- [ ] Видимый статус синхронизации и безопасное первое подключение существующего vault.

**Критерий:** тестовые сценарии не теряют содержимое, включая при закрытии клиента посреди передачи.

## 3. GitHub-режим

- [ ] Мастер подключения приватного репозитория.
- [ ] Работа на desktop, Android и iOS с заметками и вложениями в допустимых пределах GitHub.
- [ ] Инструкция по восстановлению из репозитория и сообщения об ограничениях файлов.

**Критерий внутренней alpha:** повседневная синхронизация между двумя устройствами проходит без командной строки и сохраняет историю. Технический MVP требует также этапа 4.

## 4. Режим личного VPS

- [ ] Rust-сервер, токены устройств, хранение версий и файлов.
- [ ] Установка из готового релиза, настройка HTTPS и подключение нового устройства.
- [ ] Проверка того же набора сценариев сохранности, что и для GitHub.
- [ ] Инструкция по резервному копированию и восстановлению сервера.

**Критерий технического MVP:** тестировщик поднимает сервер по инструкции и подключает два устройства без сборки кода; оба режима проходят сценарии из [MVP.md](MVP.md). Публичный релиз требует следующего этапа.

## 5. Функции первого публичного релиза

- [ ] Выборочная синхронизация типов файлов, папок и безопасных частей конфигурации vault на каждом устройстве.
- [ ] История и восстановление заметок, вложений, удалённых файлов и настроек из интерфейса плагина.
- [ ] Пользовательский выбор способа разрешения Markdown-конфликтов, пауза и журнал синхронизации.
- [ ] Приглашения, права доступа и общие vault в GitHub- и VPS-режимах.
- [ ] Клиентское шифрование VPS, безопасная передача ключей новым устройствам и участникам, политика ротации.
- [ ] Проверка ограничений GitHub, крупных вложений на VPS и защиты данных на реальных устройствах.

**Критерий:** сценарии из [RELEASE_V1.md](RELEASE_V1.md) пройдены для заявленных платформ и соответствующего backend.

## 6. Публичный релиз

- [ ] Проверка на реальных мобильных устройствах и больших vault.
- [ ] Документация по ошибкам, ограничениям и миграции формата.
- [ ] Проверка применимых правил Obsidian и подготовка полного набора файлов релиза.
- [ ] Публикация плагина в каталоге сообщества Obsidian после проверки требований каталога.

**Критерий:** релиз устанавливается по инструкции, а критические сценарии сохранности покрыты проверками.
