# Контракт ревизий v1 — черновик

Этот документ фиксирует правила принятия изменений для личного VPS. Сейчас в коде есть только [чистая модель решения](../server/src/revision.rs) и её тесты. HTTP-записи, база данных, шифрование и передача файлов ещё не реализованы. Документ **не означает**, что сервер уже безопасен для пользовательского vault.

## Граница видимости сервера

Клиент должен шифровать имена файлов, содержимое и манифест до отправки. Серверу для согласования нужны только непрозрачный ID vault, ID устройства и операции, ожидаемая и текущая ревизии, размер и контрольная сумма полученных зашифрованных байтов. Размеры, время и число операций остаются видимыми метаданными. Клиентское шифрование и модель ключей описываются отдельно до появления API записи.

## Поля и диапазон

| Поле | Правило |
| --- | --- |
| `vault_id` | Случайный непрозрачный идентификатор vault; решение принимается отдельно для каждого vault. |
| `operation_id` | Случайные 128 бит на одну логическую попытку записи. Клиент сохраняет этот ID и **те же зашифрованные байты** до подтверждения или явного пересогласования конфликта. |
| `expected_revision` | Ревизия, на основе которой клиент подготовил изменение. Первый пустой vault имеет ревизию `0`. |
| `payload_digest` | SHA-256 точных байтов зашифрованного пакета. Сервер вычисляет его сам; значение не заменяет проверку целостности шифротекста клиентом. |
| `current_revision` | Монотонная ревизия vault на сервере. Успешная новая запись увеличивает её ровно на `1`. |

На проводе ревизия будет JSON-числом от `0` до `9_007_199_254_740_991` включительно. Это верхняя граница точных целых значений, на которую можно рассчитывать при обмене с JavaScript согласно [RFC 8259, раздел 6](https://www.rfc-editor.org/rfc/rfc8259#section-6). Значения вне диапазона отклоняются. При достижении предела новые записи отклоняются, переполнение запрещено. Формат остальных полей HTTP-запроса ещё не закреплён.

## Решение о записи

Сервер сначала проверяет полномочия устройства для данного vault. После этого в одной транзакции читает текущую ревизию и запись об `operation_id` для **того же vault**. Решение принимается в таком порядке:

1. Некорректная ревизия отклоняется.
2. Если `operation_id` уже записан с теми же `expected_revision` и `payload_digest`, вернуть исходную подтверждённую ревизию. Текущая ревизия могла успеть стать больше.
3. Если ID уже записан, но ожидаемая ревизия или содержимое отличаются, отклонить повторное использование ID.
4. Если ID новый, но `expected_revision` не равна текущей, вернуть текущую ревизию как конфликт **без изменения vault**. Клиент получает изменения, пересогласует свои правки и создаёт новую операцию.
5. Если ID новый и ревизии совпадают, подтвердить новую ревизию только после атомарной записи ссылки на зашифрованный пакет и записи об операции.

Записи об уже подтверждённых ID операций нельзя удалять, пока возможен повтор старого запроса. Для v1 планируется сохранять их без срока; политика очистки потребует отдельного протокольного решения. Сервер не разрешает Markdown-конфликты: клиент сохраняет обе версии или объединяет их только при известной общей базе.

## Что должно пережить сбой

Ответ об успехе допустим только после надёжной записи новой ревизии, записи об операции и ссылок на уже сохранённые зашифрованные байты. Если ответ потерялся, повтор с тем же ID и тем же пакетом возвращает прежний результат. Если запись не завершилась, повтор может применить операцию один раз. Подтверждённая ревизия не должна ссылаться на отсутствующие объекты.

План хранения: временно принять и проверить зашифрованные объекты, затем в SQLite-транзакции проверить ревизию и добавить ссылки на них. Неиспользованные объекты после сбоя очищаются отдельно. Конкретный порядок записи на диск, `fsync`, миграции схемы, резервная копия и восстановление требуют прототипа и проверки. [SQLite допускает только одну одновременную write-транзакцию](https://www.sqlite.org/lang_transaction.html); модель решения сама по себе не даёт долговечности и не заменяет транзакцию.

Удаление файла представляется записью в зашифрованном манифесте и историей версий, а не немедленным удалением единственной копии. Как устроены манифест и хранение старых версий, ещё предстоит определить.

## Реализовано и не реализовано

- В [модели Rust](../server/src/revision.rs) проверяются конкурентные записи, повтор после более новых коммитов, изменённое содержимое при том же ID, предел ревизий и противоречивое сохранённое состояние.
- Модель не хранит данные и не вызывается HTTP-сервером. Тесты не проверяют гонки между процессами, сбои диска, авторизацию, шифрование и реальное восстановление.
- Следующий шаг — схема SQLite и интеграционная проверка атомарного применения операции и повтора после перезапуска сервера. API приёма пользовательских данных появится только вместе с авторизацией и клиентским шифрованием.
