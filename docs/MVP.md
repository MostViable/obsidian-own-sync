# MVP: внутренняя проверка self-hosted синхронизации

Этот документ описывает минимальный технический этап для проверки плагина и собственного сервера. **MVP не является первым публичным релизом**: полный состав первого релиза задан в [RELEASE_V1.md](RELEASE_V1.md). Alpha-сборки предназначены для тестирования на неважных данных.

## Что проверяем

Пользователь устанавливает плагин Obsidian на свои устройства и подключает **свой VPS**. Заметки и обычные вложения синхронизируются в обе стороны. Отключение сети, конфликт или перезапуск приложения не приводят к тихой потере данных.

Приватный репозиторий GitHub как хранилище заметок планируется после первого self-hosted релиза и в этот MVP не входит. Разработчик проекта не хранит пользовательские vault на своём сервере.

## Путь пользователя

### Личный VPS

1. Скачать готовый релиз Rust-сервера с GitHub и запустить по инструкции; компилятор Rust на VPS не нужен.
2. Подключить домен и HTTPS через Caddy либо уже работающий reverse proxy.
3. Создать vault и отдельный код подключения для каждого устройства.
4. Установить плагин на desktop и телефон; ввести адрес сервера и код или считать QR.
5. Просмотреть первое изменение vault, затем синхронизировать его и увидеть статус в Obsidian.
6. Сделать и восстановить резервную копию сервера по инструкции.

## Обязательная работа

| ID | Задача | Проверяемый результат |
| --- | --- | --- |
| M01 | Каркас плагина и сборка | Плагин загружается в desktop, Android и iOS; выполняемый код не зависит от Node.js/Electron. |
| M02 | Формат данных и протокол v1 | Описаны ID vault, ревизии, контрольные суммы, записи об удалении, версия формата и отказ от записи при устаревшей ревизии. |
| M03 | Локальное состояние | После перезапуска плагин знает подтверждённую ревизию и не теряет очередь неотправленных изменений. Не полагается только на время файлов. |
| M04 | Безопасная первая синхронизация | Мастер показывает направление и список изменений; существующие локальные файлы не заменяются без предупреждения и копии. |
| M05 | Rust-сервер | Сервер принимает объекты и ревизии, проверяет права устройства, отклоняет устаревшую запись и переживает перезапуск без потери подтверждённых данных. |
| M06 | Установка VPS | Готовые релизы для Linux x86-64 и ARM64, пример конфигурации, установка HTTPS и проверка работоспособности по инструкции. |
| M07 | Запуск синхронизации | Отправка после изменения с задержкой, получение при открытии и возвращении в приложение, ручная кнопка и повтор после ошибки. Пока приложение закрыто, синхронизация не обещается. |
| M08 | Конфликты и удаления | При несовместимых правках сохраняются обе версии; удаление другого устройства не уничтожает неотправленную правку. Автоматическое объединение текста можно добавить позже. |
| M09 | Статус и диагностика | Пользователь видит «синхронизировано», «ожидает отправки», «ошибка» и «конфликт»; журнал не содержит токенов и содержимого заметок. |
| M10 | Восстановление | Резервная копия VPS восстанавливается на чистом сервере; проверка восстановления входит в релизный сценарий. |
| M11 | Совместимость и лимиты | Плагин явно сообщает об ограничениях сервера и безопасно реагирует на несовместимую версию протокола. |
| M12 | Проверки и релиз | Автоматические сценарии движка и VPS проходят; опубликованы тестовые сборки с инструкцией установки. |

## Сценарии, которые обязаны пройти

Каждый сценарий проверяется на собственном VPS.

1. Новый файл, изменение, переименование и удаление появляются на втором устройстве после синхронизации.
2. Вложение до установленного сервером лимита передаётся без изменения содержимого.
3. Два устройства меняют **разные** файлы офлайн: после подключения сохраняются обе правки.
4. Два устройства меняют **один** файл офлайн: обе версии доступны пользователю, конфликт показан.
5. Одно устройство удаляет файл, второе правит его офлайн: правка не пропадает.
6. Передача прерывается сетью или закрытием Obsidian: после повторного запуска она завершается без потери подтверждённой версии.
7. Второе устройство подключается к уже заполненному vault; совпадающие имена не приводят к незаметной замене локальных файлов.
8. Доступ устройства отозван, сервер недоступен или диск заполнен: ошибка показана, локальная очередь сохранена.
9. Имена файлов с кириллицей, пробелами и разным регистром не смешиваются между поддерживаемыми ОС.
10. Параллельные отправки не затирают подтверждённые ревизии.
11. Резервная копия восстанавливается на чистом сервере, после чего подключается новое устройство.

## Граница MVP

- Обычные файлы vault синхронизируются независимо от формата, если их допускает сервер. Полный перенос настроек `.obsidian`, тем и плагинов переносится на следующий этап; секреты не синхронизируются.
- Клиентское шифрование VPS будет обязательным для первого публичного релиза, но в этот технический этап не входит; формат v1 проектируется с ним и с общими vault до реализации постоянного серверного хранилища. Тестовый MVP нельзя использовать для чувствительных данных.
- Совместное редактирование в реальном времени, общий облачный аккаунт проекта, GitHub как хранилище заметок, GitLab, S3 и мобильная синхронизация при закрытом Obsidian не входят в MVP.

## Условие готовности

Внутренний MVP можно назвать готовым, когда тестировщик проходит self-hosted подключение по документации, сценарии выше проходят на реальных Android и iOS, а desktop-сборки проверены на Windows, macOS и Linux. Если платформа не проверена, публичный релиз не заявляет её поддерживаемой.
