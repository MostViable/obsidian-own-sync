# MVP: первая пригодная к использованию версия

## Что проверяем

Пользователь устанавливает **один плагин Obsidian** на свои устройства и выбирает удалённое хранилище: приватный репозиторий GitHub или свой VPS. Заметки и обычные вложения синхронизируются в обе стороны. Отключение сети, конфликт или перезапуск приложения не приводят к тихой потере данных.

Оба способа хранения входят в MVP. GitHub-режим выпускается раньше как проверочная alpha; готовым MVP проект считается после проверки и VPS-режима. Разработчик проекта не хранит пользовательские vault на своём сервере.

## Путь пользователя

### GitHub

1. Установить плагин из релиза проекта на первом устройстве; после одобрения публикации — из каталога Obsidian.
2. Подключить GitHub и выбрать **отдельный приватный репозиторий** для vault. Мастер помогает создать его без терминала.
3. Просмотреть, что будет загружено, и подтвердить первую отправку существующего vault.
4. На втором устройстве установить плагин, подключить тот же GitHub-аккаунт и репозиторий, получить файлы.
5. Видеть текущий статус, ошибки и конфликты в Obsidian.

### Личный VPS

1. Скачать готовый релиз Rust-сервера с GitHub и запустить по инструкции; компилятор Rust на VPS не нужен.
2. Подключить домен и HTTPS через Caddy либо уже работающий reverse proxy.
3. Создать vault и отдельный код подключения для каждого устройства.
4. В плагине выбрать VPS, ввести адрес и код или считать QR, затем повторить на другом устройстве.
5. Сделать и восстановить резервную копию сервера по инструкции.

## Обязательная работа

| ID | Задача | Проверяемый результат |
| --- | --- | --- |
| M01 | Каркас плагина и сборка | Плагин загружается в desktop, Android и iOS; выполняемый код не зависит от Node.js/Electron. |
| M02 | Формат данных и протокол v1 | Описаны ID vault, ревизии, контрольные суммы, записи об удалении, версия формата и отказ от записи при устаревшей ревизии. |
| M03 | Локальное состояние | После перезапуска плагин знает подтверждённую ревизию и не теряет очередь неотправленных изменений. Не полагается только на время файлов. |
| M04 | Безопасная первая синхронизация | Мастер показывает направление и список изменений; существующие локальные файлы не заменяются без предупреждения и копии. |
| M05 | GitHub-подключение | Пользователь подключает выбранный приватный репозиторий без терминала; токен хранится через Obsidian `SecretStorage` и отзывается пользователем. Способ создания репозитория и минимальные разрешения приложения уточняются прототипом. |
| M06 | GitHub-адаптер | Изменения объединяются в commit; при конкурентной записи чужой commit не перезаписывается, а состояние читается заново. Ошибки лимитов API вызывают задержку и повтор, а не бесконечные запросы. |
| M07 | Rust-сервер | Сервер принимает файлы и ревизии, проверяет права устройства, отклоняет устаревшую запись и переживает перезапуск без потери подтверждённых данных. |
| M08 | Установка VPS | Готовые релизы для Linux x86-64 и ARM64, пример конфигурации, установка HTTPS и проверка работоспособности по инструкции. |
| M09 | Запуск синхронизации | Отправка после изменения с задержкой, получение при открытии и возвращении в приложение, ручная кнопка и повтор после ошибки. Пока приложение закрыто, синхронизация не обещается. |
| M10 | Конфликты и удаления | При несовместимых правках сохраняются обе версии; удаление другого устройства не уничтожает неотправленную правку. Автоматическое объединение текста можно добавить позже. |
| M11 | Статус и диагностика | Пользователь видит «синхронизировано», «ожидает отправки», «ошибка» и «конфликт»; журнал не содержит токенов и содержимого заметок. |
| M12 | Восстановление | Описано, как получить предыдущую версию из GitHub и восстановить VPS из резервной копии; проверка восстановления входит в релизный сценарий. |
| M13 | Совместимость и лимиты | Плагин явно сообщает о файлах, которые нельзя отправить через GitHub, и не пропускает их молча. Поведение при несовместимой версии протокола безопасно. |
| M14 | Проверки и релиз | Автоматические сценарии на общем механизме и обоих адаптерах проходят; опубликованы тестовые релизы с инструкцией установки. |

## Сценарии, которые обязаны пройти

Каждый сценарий проверяется для GitHub и VPS, если не указано иное.

1. Новый файл, изменение, переименование и удаление появляются на втором устройстве после синхронизации.
2. Вложение до лимита выбранного хранилища передаётся без изменения содержимого.
3. Два устройства меняют **разные** файлы офлайн: после подключения сохраняются обе правки.
4. Два устройства меняют **один** файл офлайн: обе версии доступны пользователю, конфликт показан.
5. Одно устройство удаляет файл, второе правит его офлайн: правка не пропадает.
6. Передача прерывается сетью или закрытием Obsidian: после повторного запуска она завершается без потери подтверждённой версии.
7. Второе устройство подключается к уже заполненному vault; совпадающие имена не приводят к незаметной замене локальных файлов.
8. Токен отозван, сервер недоступен или диск заполнен: ошибка показана, локальная очередь сохранена.
9. Имена файлов с кириллицей, пробелами и разным регистром не смешиваются между поддерживаемыми ОС.
10. Для GitHub: параллельные отправки не используют force push; внешний commit в репозитории не стирается.
11. Для VPS: резервная копия восстанавливается на чистом сервере, после чего подключается новое устройство.

## Граница MVP

- Обычные файлы vault синхронизируются независимо от формата, если их допускает выбранный backend. Полный перенос настроек `.obsidian`, тем и плагинов переносится на следующий этап; секреты не синхронизируются.
- Markdown в GitHub-режиме остаётся читаемым в приватном репозитории. Сквозное шифрование не заявляется для MVP; решение о нём фиксируется отдельно до проектирования формата v1.
- Совместное редактирование в реальном времени, общий облачный аккаунт проекта, GitLab, S3 и мобильная синхронизация при закрытом Obsidian не входят в MVP.
- Для обычного Git-репозитория GitHub предупреждает о файлах больше 50 MiB и блокирует файлы больше 100 MiB. Мастер должен объяснять эти ограничения до начала передачи. Отдельно проверяем лимиты выбранного способа загрузки через API.

## Условие готовности

MVP можно назвать готовым, когда пользователь проходит оба пути подключения по документации, сценарии выше проходят на реальных Android и iOS, а desktop-сборки проверены на Windows, macOS и Linux. Если платформа не проверена, релиз не заявляет её поддерживаемой.
