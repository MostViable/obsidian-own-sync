# Публикация плагина в каталоге Obsidian

## Можно ли публиковать альтернативную синхронизацию

В [правилах разработчиков](https://docs.obsidian.md/community-directory/developer-policies) нет отдельного запрета на плагины синхронизации. В каталоге уже представлены плагины с [GitHub-синхронизацией](https://community.obsidian.md/plugins/git-obsi-sync) и [личным сервером](https://community.obsidian.md/plugins/obsync-private-sync). Это показывает возможность независимого плагина, но не гарантирует одобрение нашего релиза.

Есть отдельный риск: [Terms of Service Obsidian](https://obsidian.md/terms) ограничивают использование их сервисов и ПО для разработки конкурирующего продукта или сервиса, а также копирование и обратную разработку. Как именно это положение применяется к открытому плагину с собственным хранилищем, из опубликованных документов однозначно не следует. Поэтому проект строит собственный механизм через публичный Plugin API, GitHub и VPS пользователя, не подключается к серверам Obsidian Sync и не копирует их закрытый код, протокол, интерфейс или фирменные элементы. Перед подачей релиза с заявлением о почти полном функциональном сходстве стоит запросить письменное разъяснение у команды Obsidian.

## Требования, которые закладываем заранее

- В README явно раскрыть сетевые подключения: GitHub API в режиме GitHub и адрес сервера пользователя в режиме VPS. Указать, что для первого нужен аккаунт GitHub, а для второго — свой сервер и его учётные данные. Плагин не требует аккаунта проекта.
- Не добавлять клиентскую телеметрию, скрытый исполняемый код, автоматическую установку или обновление самого плагина и зависимостей.
- Держать `LICENSE` в корне, соблюдать лицензии зависимостей и атрибуцию.
- Не создавать впечатления, что проект выпущен командой Obsidian. Отображаемое имя планируется `Own Sync`; `Obsidian` используется только для указания совместимости. Идентификатор плагина не может содержать `obsidian`; перед созданием `manifest.json` проверить уникальность кандидата `own-sync`.
- Для Android и iOS не использовать Node.js и Electron API в выполняемом коде. `minAppVersion` выставить по фактически используемому API после проверки прототипа.
- Перед подачей иметь рабочие `README.md`, `LICENSE`, `manifest.json` и GitHub Release с `main.js`, `manifest.json` и, если нужен, `styles.css`. Тег релиза должен совпадать с версией в manifest.
- Проводить проверку сохранности данных на устройствах и явно описывать ограничения: синхронизация не заменяет резервную копию; параллельное использование двух систем синхронизации одного vault может приводить к конфликтам.

Правила и процедура: [Developer policies](https://docs.obsidian.md/community-directory/developer-policies), [Submission requirements](https://docs.obsidian.md/community-directory/submission-requirements-for-plugins), [Submit your plugin](https://docs.obsidian.md/plugins/releasing/submit-plugin). Перед подачей перечитать их, поскольку требования могут измениться.

## Состояние

Плагина, `manifest.json` и релиза пока нет. Проверка выше относится к концепции и плану; соответствие будущей реализации проверяется отдельно перед подачей.
