# Первый публичный релиз: близкий по возможностям к Obsidian Sync

## Цель и граница сравнения

Пользователь подключает один vault на компьютере и телефоне к своему VPS, работает офлайн, видит статус, может восстановить старую или удалённую версию и по своему выбору синхронизирует настройки. Общий vault могут использовать несколько приглашённых людей. GitHub как хранилище заметок планируется отдельным этапом после self-hosted релиза.

Цель — сопоставимый **набор пользовательских сценариев**, а не копия интерфейса, закрытого протокола или серверов Obsidian Sync. Разработка идёт через публичный Plugin API и собственный протокол; [ограничения публикации](OBSIDIAN_PUBLICATION.md) проверяются до релиза. Первый публичный релиз не объявляется готовым после одного только базового MVP из [MVP.md](MVP.md).

## Что должно работать в первом релизе

| Возможность | Проверяемый результат |
| --- | --- |
| Несколько устройств | Заметки и вложения синхронизируются в обе стороны на Windows, macOS, Linux, Android и iOS; офлайн-правки отправляются при следующем открытии или возвращении в приложение. |
| Выбор данных | На каждом устройстве можно выбрать типы файлов и исключённые папки; правила применяются до первой отправки. Скрытые файлы исключены, кроме явно разрешённой конфигурации vault. |
| Конфигурация Obsidian | Можно отдельно включить основные настройки, внешний вид, темы и сниппеты, горячие клавиши и настройки основных плагинов. Данные стороннего плагина включаются только по явному выбору: его `data.json` может содержать токены. Изменения, требующие перезапуска, показаны пользователю. Перенос исполняемого кода сторонних плагинов проверяется отдельно по правилам каталога. |
| Конфликты и удаления | Для Markdown есть объединение правок с общей базой или конфликтная копия по выбору; при удалении и конкурентной правке сохраняются обе операции. Для бинарных файлов нет тихой потери версии. |
| История и восстановление | Из плагина можно посмотреть и восстановить версии заметок, вложений, удалённых файлов и синхронизируемых настроек. Политика хранения версий задаётся явно и проверяется восстановлением. |
| Управление синхронизацией | Видны статус, очередь, ошибка и журнал без содержимого заметок и секретов; есть пауза, ручной запуск, повтор после ошибки и имя устройства. |
| Общие vault | Владелец приглашает и удаляет участников; у каждого отдельная учётная запись и устройства. Удаление доступа не стирает уже полученные человеком локальные копии. Совместное редактирование одного файла в реальном времени не обещается. |
| Безопасное подключение | Первый vault и каждое новое устройство проходят предварительный просмотр изменений. Локальные данные и настройки не затираются молча. Синхронизация и резервная копия объясняются как разные задачи. |

## Свой сервер и шифрование

- Плагин шифрует данные на устройстве до передачи. Rust-сервер хранит зашифрованные объекты и версии; ключи остаются у пользователей. Потерянный ключ сервер не восстановит: при подключении нужен проверенный способ резервного хранения ключа или фраза восстановления.
- Пользователи, приглашения, устройства и отзыв доступа реализуются на собственном сервере. Сервер управляет частотой синхронизации и поддерживает возобновляемую передачу крупных вложений; предел задаёт владелец сервера.
- История хранится как версии зашифрованных объектов и метаданные на сервере; восстановление выполняется через плагин.

Сквозное шифрование не означает, что сервер скрывает все метаданные: утечки через размеры, время и число операций оцениваются при проектировании протокола. Для общего зашифрованного vault нужны правила передачи ключа и его ротации при удалении участника. Старые копии и старые ключи нельзя отозвать задним числом.

## Принципиальные отличия от официального Sync

- Плагин запускается внутри уже открытого локального vault. Он не сможет добавить свой пункт в стартовый экран Obsidian для открытия удалённого vault; настройка начинается после создания или открытия локального vault. Это вывод из [порядка запуска плагинов](https://docs.obsidian.md/plugins/guides/load-time) и [процедуры Obsidian Sync](https://obsidian.md/help/sync/setup).
- Пока мобильный Obsidian закрыт, фоновая синхронизация не обещается. При открытии и возвращении в приложение выполняется догоняющая синхронизация; [официальный Sync тоже работает, когда приложение запущено](https://obsidian.md/help/sync/faq).
- Допустимый размер файла будет определён ресурсами собственного сервера и реализацией передачи; он может отличаться от [планов Obsidian Sync](https://obsidian.md/help/sync/plans).
- Проект не подключается к официальным серверам Obsidian Sync и не обещает совместимость с их историей, приглашениями или шифрованием.
- Автоматическая установка и обновление сторонних плагинов не обещаются до проверки правил каталога. Выбранные настройки стороннего плагина могут содержать секреты, поэтому их отправка требует отдельного предупреждения и подтверждения.

## Порядок реализации до публичного релиза

1. Завершить проверки мобильного API, конкурентной записи и формата данных. Модель формата сразу учитывает участников, историю, шифрование и возможность будущего адаптера GitHub.
2. Сделать движок, плагин и Rust-сервер; пройти базовые сценарии сохранности из [MVP.md](MVP.md) на тестовых устройствах.
3. Добавить выборочную синхронизацию и конфигурацию vault с межплатформенными тестами и восстановлением настроек.
4. Добавить историю версий, восстановление удалений, сравнение и безопасное разрешение конфликтов.
5. Реализовать пользователей и общие vault; завершить клиентское шифрование, управление ключами и отзыв доступа.
6. Пройти проверки из [issues #1, #4–#10](https://github.com/MostViable/obsidian-own-sync/issues), тесты на реальных устройствах и восстановление из резервных копий. Только затем публиковать первый релиз.
