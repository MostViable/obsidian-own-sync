# Клиентский пакет `v0` и план согласования

Это **тестовый формат** для подключения плагина к серверу. Код: [packet.ts](../src/sync/packet.ts), [plan.ts](../src/sync/plan.ts), [state.ts](../src/sync/state.ts) и [apply.ts](../src/sync/apply.ts). Плагин вручную передаёт начальный пакет между пустыми vault и может отправлять последующие локальные изменения, если удалённая ревизия не изменилась. Получение последующих ревизий ещё не реализовано. Формат `v0` не обещает совместимости с первым публичным релизом.

## Пакет

Один HTTP commit содержит UTF-8 JSON объёмом не более 1 МиБ:

```json
{
  "format_version": 1,
  "changes": [
    { "path": "Notes/example.md", "kind": "put", "bytes": "SGVsbG8=", "sha256": "185f8db32271fe25f561a6fc938b2e264306ec304eda518007d1764826381969" },
    { "path": "old.md", "kind": "delete" }
  ]
}
```

`bytes` — стандартный Base64 исходных байтов файла; `sha256` проверяет их после декодирования. Удаление не содержит байтов. В пакете хотя бы одно изменение, каждый путь встречается один раз. Декодер отвергает неизвестную версию, неверную контрольную сумму, лишние поля в записи, дубли и слишком большой пакет. Пути относительные; запрещены обход через `..`, скрытые сегменты, управляющие символы и имена, которые небезопасны на Windows. Для тестового создания файлов имя должно иметь расширение. Клиент проверяет коллизии полного пути и родительских каталогов с разным регистром; межплатформенная политика Unicode ещё нужна.

**Этот формат не шифрует содержимое и имена.** SHA-256 обнаруживает случайное повреждение, но не подтверждает отправителя и не заменяет шифрование. Его нельзя использовать с реальными или чувствительными заметками. Из-за Base64 файл размером около 750 КиБ уже может превысить лимит пакета; разбиение больших файлов на части остаётся отдельной задачей MVP.

## Трёхсторонний план

Для каждого пути клиент сравнивает SHA-256 последней подтверждённой версии (`base`), текущего локального файла (`local`) и удалённой версии после воспроизведения commit (`remote`). Отсутствие пути означает удаление.

| Состояние | Решение |
| --- | --- |
| Локальная и удалённая версии совпадают | Действие не требуется. |
| Локальная равна базе, удалённая отличается | Получить удалённую версию или удаление. |
| Удалённая равна базе, локальная отличается | Отправить локальную версию или удаление. |
| Обе стороны ушли от базы по-разному | Конфликт; сохранить обе версии до решения пользователя. |

Планировщик не применяет решения к файлам. Команда «Preview first sync» читает локальные файлы и всю историю тестового сервера, затем считает отправки, получения и конфликты относительно пустой базы. Команда «Preview changes» использует сохранённую подтверждённую базу, читает только более поздние ревизии и показывает первые восемь путей с действиями `push`, `pull` или `conflict`. Обе команды ничего не записывают и не отправляют. Каждый предпросмотр ограничен 100 читаемыми ревизиями и 32 МиБ отдельно для локальных файлов и истории сервера; случай превышения останавливает проверку. Подтверждённая база и ожидающий пакет сохраняются между перезапусками. Следующий шаг — безопасно применять последующие удалённые изменения и согласовывать конфликты. При конфликте и первом подключении существующего vault автоматическая замена файлов запрещена.

Команда «Upload test vault» отправляет все видимые локальные файлы **одним** пакетом, только когда серверный vault имеет ревизию `0`. Перед POST плагин сохраняет в `data.json` точные байты пакета и случайный ID операции. При неизвестном результате сети повтор использует те же байты и ID; подтверждённый `201` или `200 replayed` очищает ожидающую операцию. Если сервер уже занят, файл слишком большой или обнаружен небезопасный путь, новая отправка не начинается. Это начальный тест, а не общая синхронизация: последующие удалённые правки и конфликт с другой записью требуют отдельного согласования. `data.json` содержит копию файлов в открытом виде; используйте только неважные тестовые данные.

Команда «Download test vault» требует ровно ревизию `1` на сервере и пустой локальный vault. Она принимает только начальные записи `put`, проверяет пути и контрольные суммы, сохраняет пакет в `data.json` **до создания файлов**. При повторе уже созданный файл пропускается только после побайтового сравнения; отличающийся файл и посторонний локальный файл останавливают загрузку. Новые файлы создаются через Obsidian Vault API, существующие не перезаписываются. После частичной ошибки сохранённый пакет позволяет повторить создание недостающих файлов.

После подтверждения начальной отправки или получения плагин сохраняет номер ревизии и SHA-256 каждого файла как локальную базу. Команда «Push local changes» сравнивает текущие файлы с ней, формирует один пакет `put`/`delete` только для отличий и требует, чтобы текущая ревизия сервера совпадала с базой. Точные байты пакета, ID операции и ожидаемая ревизия сохраняются до POST; потерянный ответ повторяется с теми же значениями. При `409` пакет остаётся в очереди, локальные файлы не меняются.
