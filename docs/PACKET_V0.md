# Клиентский пакет `v0` и план согласования

Это **тестовый формат** для подключения плагина к серверу. Код: [packet.ts](../src/sync/packet.ts), [plan.ts](../src/sync/plan.ts) и движок синхронизации [engine.ts](../src/sync/engine.ts). Формат `v0` не обещает совместимости с первым публичным релизом.

## Пакет

Один HTTP commit содержит UTF-8 JSON не больше лимита, который сервер сообщает в `/api/v0/capabilities` (сейчас 1 МиБ; плагин принимает до 64 МиБ):

```json
{
  "format_version": 1,
  "changes": [
    { "path": "Notes/example.md", "kind": "put", "bytes": "SGVsbG8=", "sha256": "185f8db32271fe25f561a6fc938b2e264306ec304eda518007d1764826381969" },
    { "path": "old.md", "kind": "delete" }
  ]
}
```

`bytes` — стандартный Base64 исходных байтов файла; `sha256` проверяет их после декодирования. Удаление не содержит байтов. В пакете хотя бы одно изменение, каждый путь встречается один раз. Декодер отвергает неизвестную версию, неверную контрольную сумму, лишние поля в записи, дубли и слишком большой пакет. Пути относительные; запрещены обход через `..`, скрытые сегменты, управляющие символы и имена, которые небезопасны на Windows. Для тестового создания файлов имя должно иметь расширение. Клиент проверяет коллизии полного пути и родительских каталогов с разным регистром; межплатформенная политика Unicode ещё нужна.

**Этот формат не шифрует содержимое и имена.** SHA-256 обнаруживает случайное повреждение, но не подтверждает отправителя и не заменяет шифрование. Его нельзя использовать с реальными или чувствительными заметками. Из-за Base64 в пакет помещается файл примерно до ¾ лимита минус 64 КиБ запаса (при лимите 1 МиБ — около 720 КиБ). Большие файлы плагин не отправляет и показывает их список; синхронизированная ранее версия такого файла на сервере не удаляется.

## Трёхсторонний план

Для каждого пути клиент сравнивает SHA-256 последней подтверждённой версии (`base`), текущего локального файла (`local`) и удалённой версии после воспроизведения commit (`remote`). Отсутствие пути означает удаление.

| Состояние | Решение |
| --- | --- |
| Локальная и удалённая версии совпадают | Действие не требуется. |
| Локальная равна базе, удалённая отличается | Получить удалённую версию или удаление. |
| Удалённая равна базе, локальная отличается | Отправить локальную версию или удаление. |
| Обе стороны ушли от базы по-разному | Конфликт: локальный файл остаётся на месте, удалённая версия сохраняется рядом как `имя (conflict ГГГГ-ММ-ДД ЧЧ-ММ-СС).расширение`, затем обе уходят на сервер. |
| Одна сторона удалила, другая изменила | Правка побеждает: удалённая правка восстанавливает файл, локальная правка отправляется заново. |

## Цикл синхронизации

Состояние движка хранится в каталоге плагина, вне синхронизируемого vault: `sync-state.json` (подтверждённая ревизия и SHA-256 файлов на ней), `pending-upload.json` (точные байты отправляемого пакета) и `hash-cache.json` (хэши по времени изменения и размеру, чтобы не перечитывать неизменённые файлы; ручной «Sync now» пересчитывает все хэши). Один цикл:

1. Проверить `/api/v0/capabilities` и взять лимит пакета.
2. Если есть сохранённая отправка — повторить её с тем же ID и байтами. `201 applied` или `200 replayed` продвигают базу. `409` доказывает, что операция не применена (сервер проверяет ID до ревизии), поэтому пакет удаляется, а его изменения заново берутся из локальных файлов.
3. Получить новые ревизии порциями до 16 МиБ, построить трёхсторонний план и применить его: удаления через `FileManager.trashFile` по настройке корзины, записи через Vault API, conflict-копии для правок одного пути. Перед каждой записью файл проверяется ещё раз; если пользователь изменил его после сканирования, цикл прерывается без записи и повторяется через несколько секунд. База продвигается только после применения всей порции.
4. Отправить локальные отличия от базы пакетами не больше лимита. Каждый пакет сохраняется до POST; ревизия сервера должна совпадать с базой. При конфликте ревизий цикл возвращается к шагу 3.

Любой шаг можно прервать. Повторный цикл заново строит план от базы: уже применённые файлы совпадают с сервером и пропускаются, уже созданная conflict-копия с тем же содержимым используется повторно. Повреждённое или чужое состояние начинает слияние с пустой базой, а оно никогда не удаляет файлы. Если сервер восстановлен из более старой резервной копии и его ревизия меньше базы, плагин так же сливает vault заново. Файлы с неподдерживаемыми именами (без расширения, с запрещёнными в Windows символами) пропускаются и показываются в статусе; имена, отличающиеся только регистром, останавливают синхронизацию до переименования.

Автоматическая синхронизация запускается через 1,5 секунды после изменения vault, при возвращении приложения, восстановлении сети и каждые 30 секунд. Работа при закрытом мобильном Obsidian не обещается.
