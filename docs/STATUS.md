# Состояние работ

Обновлено: 2026-09-25.

## Сделано

- Создана начальная документация идеи, архитектуры, решений, дорожной карты и GitHub-процесса.
- Подробно определены состав MVP и сценарии проверки для личного VPS.
- Создан локальный Git-репозиторий с веткой `main`.
- Создан публичный репозиторий [MostViable/obsidian-own-sync](https://github.com/MostViable/obsidian-own-sync), добавлен `origin`, принята лицензия MIT.
- Заведены [issues #1–#10](https://github.com/MostViable/obsidian-own-sync/issues) для технических проверок, сравнения конкурентов и вопроса по правилам публикации. Issues #2–#3 перенесены на этап после self-hosted релиза.
- Сверены действующие правила публикации в каталоге Obsidian; выводы и проверки записаны в [OBSIDIAN_PUBLICATION.md](OBSIDIAN_PUBLICATION.md).
- Первый публичный релиз переопределён как близкий по возможностям к Obsidian Sync на личном VPS, включая общие vault и шифрование до отправки. GitHub как хранилище читаемого Markdown перенесён на этап после релиза; состав и ограничения записаны в [RELEASE_V1.md](RELEASE_V1.md) и [ROADMAP.md](ROADMAP.md).
- Сравнены существующие решения из каталога Obsidian; выводы и ограничения поиска записаны в [COMPETITORS.md](COMPETITORS.md).
- Добавлены каркас Obsidian-плагина, Rust-сервер с `/healthz` и GitHub Actions для сборки обеих частей. `npm ci`, `npm run build` и первая проверка `cargo check` в CI прошли. В плагине есть ручная проверка соединения с личным сервером; синхронизации файлов ещё нет.
- Зафиксирован [контракт ревизий](REVISION_CONTRACT.md) и добавлена чистая модель принятия записи в Rust с тестами конкуренции и повторов.
- Добавлено [SQLite-хранилище](STORAGE.md): пакет, ID операции и ревизия сохраняются одной транзакцией. На этапе хранилища прошли 13 Rust-тестов, включая повтор после открытия базы, конкуренцию двух соединений, откат после ошибки и обнаружение повреждённого пакета.
- Добавлена внутренняя [модель доступа](ACCESS.md): отдельные отзывные токены устройств, роли участников vault и миграция схемы SQLite 1 → 2. Локально прошли 17 Rust-тестов. Публичного входа и приглашений ещё нет.
- Добавлен выключенный по умолчанию экспериментальный [HTTP API `v0`](PROTOCOL_V0.md) для чтения ревизии, получения пакета и конкурентной записи с токеном устройства. На этапе API прошли 22 Rust-теста. Сетевой выдачи токенов и клиентского шифрования нет.
- Добавлена локальная команда [bootstrap](BOOTSTRAP.md): она создаёт новую тестовую базу и закрытый файл с первым токеном. API теперь требует существующую базу и не создаёт пустую при ошибке пути. Локально прошли 26 Rust-тестов.
- Плагин получил ручную проверку доступа к тестовому vault. Он хранит в настройках ID vault и имя секрета, а значение токена читает из Obsidian SecretStorage только при запросе. Для этого требуется Obsidian 1.11.4 или новее. Файлы по-прежнему не синхронизируются.
- Добавлены [тестовый клиентский пакет и чистый планировщик](PACKET_V0.md) для двоичных файлов, удалений и обнаружения параллельных правок. Локальные тесты проверяют повреждение пакета, предел размера, опасные пути, первую синхронизацию и конфликт изменения с удалением. Ручной предварительный просмотр не меняет vault и не отправляет файлы.
- Добавлена ручная отправка всех видимых файлов тестового vault одним пакетом только на пустой сервер. Перед запросом плагин сохраняет точные байты и ID операции в `data.json` для безопасного повтора; файлы на устройстве не меняются. Пакет и локальная копия **не зашифрованы**, поэтому это только тест с неважными данными. Локальный HTTP smoke-тест подтвердил `201 applied`, повтор `200 replayed` и чтение исходного пакета.
- Добавлено ручное получение первой серверной ревизии во второй пустой тестовый vault. Пакет сохраняется до применения; при повторе плагин сравнивает существующие файлы побайтово и не перезаписывает расхождения. Локальные тесты проверяют частичное создание и продолжение. Ручной запуск внутри Obsidian на устройствах ещё не проверен.
- После начального обмена плагин сохраняет подтверждённую ревизию и хэши файлов. Ручная команда отправляет последующие локальные добавления, правки и удаления только при совпадении ревизии сервера; пакет сохраняется для идентичного повтора. Локальный HTTP smoke-тест подтвердил ревизии 2 и 3, повторы и удаление. При конфликте с удалённым изменением очередь остаётся, автоматического согласования пока нет.
- Команда «Preview changes» читает ревизии после последней подтверждённой, сравнивает их с локальными файлами и показывает первые восемь путей со статусом отправки, получения или конфликта. Подтверждённое состояние и ожидающий пакет не меняются. Тесты покрывают удалённую правку, удаление, локальную офлайн-правку и конфликт путей.
- Команда «Pull remote changes» применяет новые серверные изменения. Итоговый пакет сохраняется до записи; повтор проверяет исходные и уже применённые файлы, удаление переносит файл в корзину Obsidian. Тесты проверяют прерывание, повтор, локальную правку и переход файла в каталог.
- Получение теперь принимает независимые локальные и удалённые правки: затронутые сервером пути применяются, локальные изменения других файлов остаются для следующей отправки. План проверяет структуру путей после применения, поэтому допустимая замена файла каталогом не блокируется; конфликт одного пути по-прежнему останавливает операцию.
- Добавлена команда пересогласования ожидающей отправки после подтверждённого `409 conflict`: сначала проверяется идентичный повтор, затем совпадение локальных файлов с сохранённым пакетом, далее независимые серверные изменения применяются с возобновлением и локальные правки отправляются новым ID. Перед повторным применением и после него проверяется локальное состояние; ответ `operation_id_reused`, правка того же пути и изменение локальных байтов после постановки в очередь не снимают старый пакет. Прошли 31 клиентский тест и сборка плагина. Ручной сценарий в Obsidian ещё не проверен.
- Добавлен выключенный по умолчанию автоматический цикл после первого подтверждённого обмена: debounce 1,5 секунды на create/modify/delete/rename, запуск при возвращении приложения и восстановлении сети, status bar со статусами настройки, синхронизации, очереди, конфликта и ошибки. Начальная синхронизация остаётся ручной. Ручной запуск на desktop и mobile ещё не проверен.
- Добавлена локальная команда `provision`: owner credentials выпускают отдельный отзывный токен для второго устройства и новый закрытый JSON-файл. Плагин и документация больше не требуют раздавать первый bootstrap-токен. Сетевых приглашений участников пока нет.
- Добавлена команда сервера `backup`, использующая SQLite `VACUUM INTO` без перезаписи существующего файла; Rust-тест открывает backup как восстановленную базу и проверяет сохранённую ревизию и пакет. Проверка на реальном VPS ещё не выполнена.
- Добавлены workflow релиза для плагина и серверных архивов Linux x86-64/ARM64, systemd unit, пример Caddy и инструкция [VPS.md](VPS.md). Релизный workflow ещё не запускался тегом, установка и восстановление на реальном VPS не проверены.
- Экспериментальный API сообщает версию протокола, формат пакета и лимит через `/api/v0/capabilities`; плагин проверяет ответ перед каждой ручной и автоматической операцией и останавливается при несовместимости. Это защита для `v0`, а не готовый протокол `v1`.
- CI теперь выполняет серверный smoke-сценарий: `bootstrap`, `provision`, health/capabilities, запись и повтор пакета, `backup`, запуск восстановленной базы и проверка ревизии. Реальный VPS и устройства по-прежнему не заменены этим тестом.
- Ручные тестовые команды заменены единым движком синхронизации [engine.ts](../src/sync/engine.ts): цикл «повтор отправки → получение порциями → отправка пакетами до лимита сервера». Первое подключение сливает непустые vault; правки одного пути сохраняются как conflict-копии, правка побеждает удаление. Кэш хэшей по времени и размеру убирает перечитывание vault, автоцикл не показывает уведомления без ошибок и конфликтов. Лимиты 1 МиБ на весь обмен, 32 МиБ и 100 ревизий сняты: большие файлы пропускаются с предупреждением, без удаления на сервере. 17 сценарных тестов движка с сервером в памяти проверяют сценарии MVP 1–11, кроме зависящих от устройств, включая обрыв посреди применения, потерянный ответ, параллельные отправки и сервер после восстановления из копии. Ручной запуск в Obsidian ещё не выполнен.

## Сейчас

Стадия alpha-синхронизации. Движок покрыт сценарными тестами, но в Obsidian на устройствах и на реальном VPS ещё не проверялся. Шифрования и общих vault нет.

## Следующие действия

Цель MVP (решено 2026-09-25): на VPS одна команда устанавливает сервер со встроенным HTTPS и печатает код подключения с QR; в плагине пользователь вводит только код, дальше синхронизация автоматическая. Один код подходит для всех устройств, каждое получает свой отзывной токен.

1. Сервер: обмен кода подключения на токен устройства, команды `setup`, `code`, `devices`, `revoke`, настраиваемый лимит пакета, встроенный HTTPS через Let's Encrypt.
2. Установщик `install.sh` одной командой.
3. Плагин: поле кода подключения вместо ручных настроек, автосинхронизация по умолчанию, журнал синхронизации.
4. E2E-сценарии в CI с настоящим сервером, проверка в desktop Obsidian, затем alpha-релиз и проверка на VPS и телефоне.
5. После MVP: протокол `v1` с шифрованием, историей и общими vault (issues #4, #6–#8), [issue #10](https://github.com/MostViable/obsidian-own-sync/issues/10) и вопрос по правилам Obsidian ([issue #9](https://github.com/MostViable/obsidian-own-sync/issues/9)).
